# 度量口径与可信度

## 1. 单请求指标（以 analyze.py 为例）

| 指标 | 定义 | 坑 |
|---|---|---|
| TTFT | 第一个**携带生成 token** 的 chunk 时刻 − 发送时刻 | role chunk 不算 |
| TPOT | (最后 token 时刻 − 首 token 时刻) / (completion_tokens − 1) | 单 token 请求无定义 |
| ITL | 相邻 token chunk 间隔；另有按 token 数加权的 itl_per_token | ITL ≠ TPOT（p90 可差 3–4 倍） |
| E2E/TTLT | 请求总耗时 | |
| send_lag | 客户端调度到真正发出的时间 | 过大说明客户端拖累吞吐 |

## 2. 统计窗口（steady）

```
ws = max(首个完成, 起点 + trim_head)
we = 最后一次 send − trim_tail
有效条件：窗长 ≥ max(5 s, 5% 总时长)
```

- 输出 token/s：窗口内 **token 到达**之和 ÷ 窗长（不是按请求归属）
- prompt token/s：**首 token 落在窗口内**的请求的 prompt 之和 ÷ 窗长
- 吞吐口径：`(prompt + output) / 窗长 / GPUs`，**含缓存命中的输入 token**
- 另报窗口前 1/3 与后 1/3 的 TTFT p50 —— 用来发现"窗口内仍在漂移"

## 3. keep-up（开环是否跟得上）

`completion_over_arrival = 窗内完成数 ÷ 窗内到达数`；`keeps_up = ≥ 1 − 5%`。
`NOT-keeping-up` 的点的延迟无意义，不能当性能点。

## 4. SLO 判定

默认在**窗口内发出的请求**上算：TTFT p50 ≤ 2.5 s、p99 ≤ 5 s、TPOT p90 ≤ 20 ms。
单项可以为 None（不适用），只有非 None 项参与"全部通过"。

## 5. 收入/价值模型

价格按你的目录价配置（下文以"示例价 $8 / $2 / $28 每百万 token"演示：新输入/缓存命中/输出）；目标 X 万元/32 卡月。
`CNY/GPU-h = CNY/s × 3600 / GPUs`；`CNY/32卡月 = CNY/GPU-h × 32 × 720`。
两个版本：(a) 实测完成量；(b) 设定到达率 × 设计 token 数——**对外用 (b)**，但要声明。

## 6. 可信度阈值（实测经验，可直接引用）

| 指标 | 单次运行不确定度 | 说明 |
|---|---|---|
| 10 分钟泊松吞吐 | **±1%** | 1.4–3.2 万请求 → 计数噪声 0.6–0.8% |
| TTFT p50 | ±10–30% | 多 seed 短跑 |
| **TTFT p99** | **±40%** | 单次运行，不要用它做 1% 级决策 |
| SLO 边界 | ±1 档（1–2%）且**偏乐观** | 3 分钟短跑比 10 分钟高估 5–7% |
| 长稳漂移 | 10 分钟内最后 1/3 的 p50 比整窗高 **25–51%** | 1 小时级结论需要另测 |
| 低并发点（c1–c8） | p99 由 1 个样本决定 | evalscope c1 只有 25–51 个请求 |
| GSM8K（1,319 题） | stderr ≈ 0.40–0.46pp（95% CI ±0.8–0.9pp） | 小于 0.8pp 的差异不显著 |

## 7. 指标口径陷阱

- **总吞吐 ≠ 计算量**：90% 命中 + 长输入时输出只占 0.8%；8k/0% 时占 11%。跨命中率比较必失真。
- **不同生成器的 steady 定义不同**（evalscope 闭路 vs 压测客户端泊松）→ 不能混着比。
- **p95 常常没有**：很多实现只出 p50/p90/p99，表格里宁缺勿造。
- **simulate-acc 固定接受长度**只影响 TPOT/吞吐，不影响 TTFT；不能与真实接受长度混比。
