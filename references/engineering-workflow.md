# 工程管理流程

## 阶段与出口

| 阶段 | 主要问题 | 必须产物 | 出口条件 |
|---|---|---|---|
| Scope | 要优化什么，哪些资源可用 | 范围、风险、资源清单 | 权限和边界明确 |
| Baseline | 当前系统到底是什么 | 部署快照、anchor run | 可复现且证据完整 |
| Explore | 哪类变量值得继续 | 迭代页、低成本结果 | 候选通过初级门禁 |
| Confirm | 收益是否稳定 | 重复/长稳态结果 | 正确性、SLO、稳定性通过 |
| Package | 如何交给他人复现 | recipe、索引、最小补丁说明 | dry-run 与静态检查通过 |
| Review | 结论是否可信 | 报告、证据映射、遗留项 | 数字可回算、敏感信息已移除 |

## 计划写法

每个阶段计划只需要回答：

1. 假设是什么；
2. 固定哪些条件；
3. 修改哪些变量；
4. 用什么门禁晋级；
5. 失败如何回滚；
6. 何时停止探索。

为长任务设置固定 cadence。每个检查点必须产生可检查证据，例如一个可运行脚本、一个 run-id、一次失败归因或一项明确决策，不能只报告“仍在测试”。

## 资源和所有权

- 给每条实验臂分配 GPU、端口、容器名前缀、结果根目录和缓存根目录。
- 启动前验证所有权；不抢占未知进程，不使用宽泛通配符清理。
- 记录谁可以修改部署、谁可以执行压测、谁负责验收。
- 有外部依赖时，把等待状态写入台账，同时推进不依赖它的静态整理或分析。

## 变更控制

- 基线冻结后，所有运行时或代码变化都生成新的 config-id。
- 原生配置优先于代码补丁；补丁优先于不可追溯的容器内临时修改。
- 任何容器内临时修改必须导出 diff、适用 revision 和回滚方式，才能进入确认阶段。
- 不把多个来源的脚本直接覆盖合并；先保留来源边界，再提取公共层。

## 验收与移交

验收按层分开记录：静态正确、可启动、健康、可生成、数据路径真实、性能达标。前一层通过不等于后一层通过。

移交包应能让未参与调优的人回答：用哪个入口、依赖什么、如何 dry-run、怎样启动/停止、如何验证、证据在哪里、有哪些已知限制。
